VERDICT: CHANGES

- Verified empirically (vitest probe against the real schemas, since the package is TS-source): NaN cannot arrive via `cents_per_point` / `points_amounts` / `valuations` — Zod `positive()`/`int()` reject it. Overflow to Infinity needs ~1e300 inputs and only yields a failing output parse; not a finding.
- Prototype-chain lookups are the real gap. `faceValueFor` (compute.ts:71,75) reads `input.points_amounts[benefitId]` and `input.cents_per_point[input.card.currency_id]` with bare bracket access, and `scaleValue` (compute.ts:55) reads `input.valuations[benefitId]` the same way. For the schema-valid key `currency_id: '__proto__'` (or `constructor`), the lookup returns `Object.prototype`/`Function` instead of `undefined`, so the `?? default` fallback never fires and `Math.round(points * Function)` → NaN face value and NaN totals from input that passed `RoiInputSchema.parse`. Worse, `input.ts:59` uses `inst.benefit_id in input.benefits`, so an instance referencing `toString`/`constructor` bypasses the unknown-id reject entirely. Concrete fix (all inside this job's scope, compute.ts): guard with `Object.hasOwn(...)` at the three lookup sites (or `Object.create(null)`-backed records) so inherited keys fall through to zero/default; note the `in`-check in `input.ts` to the orchestrator as a fenced-out follow-up.
- No second validation layer was added — `computeCardRoi` correctly trusts `RoiInputSchema` verbatim per spec; `input.ts`/`instanceKey`/`RoiInputSchema` untouched in the diff (exactly two files changed).
- No new dependencies (`currencies` comes from the pre-existing `@ccrt/catalog` workspace dep), no I/O, no routes/db/env/secrets — nothing touches the project invariants (card numbers, export/delete, aggregator tokens, attack surface). Pure-function blast radius is the NaN propagation above.
